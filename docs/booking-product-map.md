# نقشهٔ صفحات و مسیر رزرو ورزشا

## صفحات نسخهٔ اول

| مسیر | هدف | دادهٔ اصلی |
| --- | --- | --- |
| `/` | معرفی پلتفرم و شروع جست‌وجو | رشته، شهر، زمین‌های منتخب |
| `/court` | جست‌وجوی زمین | شهر، رشته، تاریخ، نتایج و فیلترها |
| `/court/[sport]` | فهرست زمین‌های یک رشته | باشگاه، زمین، قیمت و سانس‌های نزدیک |
| `/court/reserve/[slug]` | معرفی باشگاه و انتخاب زمین | اطلاعات باشگاه، زمین‌ها و بازه‌های آزاد |
| `/court/reserve/[slug]/checkout` | ثبت درخواست رزرو | سانس انتخاب‌شده و اطلاعات تماس |
| `/account/bookings` | مشاهده و لغو رزروهای کاربر | رزروها و وضعیت آن‌ها |

مسیرهای همبازی (`/partner`)، مربی (`/coach`)، مسابقات (`/tournaments`) و همکاری باشگاه (`/colab`) در نقشهٔ محصول می‌مانند؛ توسعهٔ آن‌ها بعد از کامل شدن مسیر اصلی رزرو انجام می‌شود.

## جریان رزرو

۱. کاربر رشته، شهر و تاریخ را جست‌وجو می‌کند.
۲. صفحهٔ باشگاه را باز می‌کند و زمین موردنظر را انتخاب می‌کند.
۳. سانس‌های آزاد همان روز را می‌بیند و یکی را انتخاب می‌کند.
۴. شمارهٔ تماس و نام را ثبت می‌کند؛ رزرو برای مدت محدود در وضعیت انتظار پرداخت نگه داشته می‌شود.
۵. بعد از اتصال درگاه، پرداخت موفق رزرو را قطعی می‌کند؛ انصراف یا انقضای مهلت، سانس را آزاد می‌کند.

در نسخهٔ اولیه می‌توان مرحلهٔ پرداخت را به حالت «رزرو آزمایشی/در انتظار پرداخت» محدود کرد. تأیید شماره با OTP و پرداخت واقعی، اتصال بیرونی جداگانه می‌خواهد.

## مدل زمانی و رزرو

- `CourtSchedule`: ساعات کاری تکرارشوندهٔ هر زمین در روز هفته، با زمان شروع/پایان، مدت سانس و فاصلهٔ بین سانس‌ها.
- `CourtClosure`: تعطیلی یا بازهٔ غیرقابل‌رزرو برای یک زمین.
- `Booking`: زمین، کاربر اختیاری، نام و تلفن تماس، زمان شروع/پایان، مبلغ، وضعیت رزرو و زمان انقضای نگه‌داشت موقت.
- زمان‌های ورودی و خروجی API باید ISO-8601 باشند. قواعد ساعات کاری با منطقهٔ زمانی `Asia/Tehran` تفسیر و زمان نهایی به‌صورت UTC ذخیره شود.
- دو رزرو فعال برای یک زمین نباید هم‌پوشانی داشته باشند. این قاعده باید داخل تراکنش دیتابیس بررسی شود تا دو درخواست هم‌زمان نتوانند یک سانس را بگیرند.

## تطبیق با کد فعلی

Next.js/NestJS/PostgreSQL/Prisma مناسب باقی می‌ماند. `Club` و `Court` موجودند و `Booking` شروع خوبی است، اما برنامهٔ ساعات کاری، تعطیلی زمین، اطلاعات تماس مهمان و زمان انقضای نگه‌داشت موقت در مدل فعلی وجود ندارند. فرانت‌اند فعلاً فقط صفحهٔ خانه دارد و API فقط فهرست زمین‌ها و بازیکنان را می‌خواند؛ پس صفحه‌های فهرست، جزئیات/انتخاب سانس، ایجاد رزرو و مشاهدهٔ رزروها باید اضافه شوند.

## اپلیکیشن موبایل

وب و اپ موبایل باید از همان REST API استفاده کنند. برای Android و iOS، React Native با Expo و TypeScript انتخاب پیشنهادی است؛ این انتخاب زبان و قراردادهای API را با پروژهٔ فعلی هم‌راستا نگه می‌دارد. اپ موبایل در گام بعدی به‌صورت workspace جدا (`apps/mobile`) اضافه می‌شود و احراز هویت OTP باید پیش از ارائهٔ عمومی در هر سه کلاینت مشترک باشد.
